## 2. 真机实测中发现并修复的边界缺陷

在 4× RTX 4090 容器环境对 `8,432.2s`（140.5 分钟，`854x480 @ 59.94 fps`，共 `505,425` 帧）真实长视频样本进行热更新实测过程中，定位并修复了以下 5 项只有在真实多卡硬件与生产片源上才会暴露的关键边界问题：

1. **多线程 TensorRT 上下文设备绑定（`jasna/trt/trt_runner.py`、`jasna/multi_gpu.py`）**：
   - 现象：多线程池（`Stage1Scan` / `MultiGpuSpan`）在新线程中反序列化 TensorRT 引擎时，若未显式调用 `torch.cuda.set_device(self.device)`，TensorRT Runtime 默认将上下文绑定在 `cuda:0`，与 `cuda:1..3` 输入张量产生跨卡地址冲突。
   - 修复：在 `TrtRunner._setup()`、`TrtRunner.infer()` 及 `multi_gpu.py` 各工作线程入口统一绑定目标 `torch.cuda.set_device(device)`。
2. **H.264 开放 GOP（Recovery Point SEI）随机访问关键帧识别（`jasna/media/splice.py`）**：
   - 现象：生产片源（x264 编码）仅第 0 帧为 IDR（`nal_type == 5`），其余 3,692 个容器关键帧均为携带内联 `SPS(7) + PPS(8) + Recovery Point SEI(6) + I-Slice(1)` 的开放 GOP 关键帧；原 `_is_safe_random_access_packet()` 仅检查 `5 in nal_types`，导致全片仅识别出 1 个关键帧，无法切分跳过无码段。
   - 修复：支持携带内联 `SPS(7) + PPS(8) + I-Slice(1)` 的 H.264 容器关键帧及 HEVC `CRA_NUT(21)`，全片 `3,693` 个关键帧（平均间隔 `2.28s`）全部正常识别且经 NVDEC 验证零丢帧解码。
3. **子进程继承 `JASNA_MAIN_PID` 导致 Worker 秒退（`jasna/multi_gpu.py`）**：
   - 现象：主控进程在 `jasna/__main__.py` 中写入 `os.environ["JASNA_MAIN_PID"] = str(os.getpid())`；当 `multi_gpu.py` 启动 `$JASNA_RELEASE_BIN` 子进程时继承了该环境变量，子进程启动完成运行时校验后触发 `str(os.getpid()) != _JASNA_MAIN_PID` 守卫并直接 `sys.exit(0)`。
   - 修复：在 `_render_mosaic_span_on_gpu` 与 `_run_l2_collaborative_track_denoise` 启动子进程前清理 `env.pop("JASNA_MAIN_PID", None)`，设置 `PYTHONIOENCODING=utf-8`，并在子进程结束后强制校验输出文件存在性。
4. **源码树与加密模型运行时协同探测（`jasna/license_api.py`）**：
   - 现象：容器内挂载源码目录时存在空的 `jasna/protection/__init__.py`，导致 `find_spec("jasna.protection")` 误判存在受保护模块而未将 `.safetensors.enc` 交由 `$JASNA_RELEASE_BIN` 处理。
   - 修复：`protection_available()` 进一步检查 `find_spec("jasna.protection.protected_tensors") is not None`。
5. **容器入口脚本隐藏缓存目录过滤与离线机器码恢复（`.drone/entrypoint.sh`）**：
   - 修复：`find "$SCAN_DIR"` 增加 `-not -path "*/.*"` 排除 `.jasna-resume` 临时分片目录，并支持从持久化目录自动恢复 `/etc/machine-id` 以匹配离线许可证。

## 3. 执行与实测验证记录（4× RTX 4090）

### 3.1 Stage 1：4 卡并行 `1 fps` 预扫与无码跳过实测

- **测试样本**：长视频样本 A（时长 `8,432.17s` / `140.5` 分钟，`854x480 @ 59.94 fps`，总帧数 `505,425` 帧，原片码率 `2,131 kbps <= 5,000 kbps`，自动触发 `PRESERVE_LOW_BITRATE=true` 低码率不压缩保护）。
- **4 卡并行扫描耗时**：4 张 RTX 4090 同时加载 `rfdetr-v6-large.bs1-4.fp16.linux.engine`、姿态关键点模型与 `VALI NVDEC` 硬件解码器，全片 `8,426` 个采样点扫描总耗时 **`84.19s`**（折合 **`100.1x` 实时倍速**，约 `6,003 fps` 原片等效扫描速率）。
- **无码与纯人头码跳过率**：
  - 全片共检出 `3,833` 个有效含码采样点（阈值 `0.40`）。
  - 有效修复总时长 **`4,215.3s`（占全片 `50.0%`）**；无马赛克及仅含男优人头打码的跳过总时长 **`4,216.9s`（占全片 `50.0%`，合计 70.3 分钟）**。

### 3.2 人头马赛克剔除与姿态模型升级对比（T6 验证）

- 在同一视频 4 个不同时间段（共 `205` 帧含码画面）上实测对比 `yolov8n-pose.pt` 与 `yolo26s-pose.pt`：
  - `yolov8n-pose.pt`：姿态过滤总耗时 `1.23s`（**`5.99 ms/hit-frame`**），剔除人头马赛克框 **23 个**，保留核心部位马赛克框 **184 个**。
  - `yolo26s-pose.pt`：姿态过滤总耗时 `1.27s`（**`6.17 ms/hit-frame`**，GPU 预缩放到 `640` 后单帧仅差 `0.18 ms`），剔除人头马赛克框 **37 个**（侧脸与半遮挡场景检出率提升 **`+60.9%`**），保留核心部位马赛克框 **170 个**，核心部位零误杀。

### 3.3 Stage 2：单容器 4 卡并行 LTX 22B 修复与冷启动耗时拆解

- **4 卡并发硬件负载（`nvidia-smi` 实测）**：
  - 帧级扫描阶段（Pass 1 `scan`）：4 卡并发吞吐达 `229.5 + 226.9 + 225.8 + 226.1 = 908.2 frame/s`，单卡功耗 `343W ~ 364W`（4 卡合计 `1,404W`）。
  - 3D VAE 编码阶段（Pass 2 `encode`）：4 卡显存占用 `6,921 ~ 7,155 MiB`，单卡峰值吞吐 `1,154 frame/s`、稳态 `95 ~ 145 frame/s`，GPU 利用率 `100%`。
  - 22B DiT 去噪阶段（Pass 3 `denoise`，INT8 Triton 算子）：4 张 RTX 4090 同时达到 **`100%` 利用率**，显存占用分别为 **`17,747 MiB`、`18,119 MiB`、`17,879 MiB`、`19,453 MiB`**，单卡功耗分别为 **`449.67W`、`450.67W`、`450.07W`、`450.01W`**（4 卡合计 **`1,800.42W`**，全部跑满 450W TDP），单卡去噪速率稳定在 **`1.51 ~ 1.55 step/s`**，4 卡并发总吞吐达 **`6.12 step/s`**（相比单卡 `1.54 step/s` 实现 **`3.97x` 线性加速**）。
  - 3D VAE 解码合成阶段（Pass 4 `compose`）：4 卡并发合成速率稳定在单卡 `50.4 ~ 82.3 frame/s`（4 卡合计 `~240 frame/s`）。
- **单次 Worker 22B 模型冷启动与四阶段耗时占比（以 `~115s` / `7,108` 帧分段实测为例）**：
  - 子进程启动 + 运行时校验 + CUDA/TRT 初始化：**`10.5s ~ 11.0s`**
  - Pass 1 `scan`（`7,108` 帧）：**`31s ~ 33s`**（占 `8.2%`）
  - 3D VAE 编码器加载 + Pass 2 `encode`：**`3.0s` 加载 + `87s ~ 95s` 编码**（占 `24.1%`）
  - 22B DiT 加密权重解密加载 + Triton 预热 + Pass 3 `denoise`（`160~168` 步）：**`~13s` 加载 + `95s ~ 109s` 去噪**（占 `27.3%`）
  - VAE 解码器加载 + Pass 4 `compose`：**`~3s` 加载 + `124s ~ 140s` 合成**（占 `33.8%`）
  - **结论**：单次 worker 进程启动与三阶段模型加载的固定冷启动开销合计约 **`29s ~ 32s`**（约占 115s 分段总耗时的 `7%`）。采用 T7 按卡大块归并后，全片 worker 启动与 22B 模型加载次数由 **84 次降至 6 次**，直接消除 `78 × ~30s = 2,340 GPU 秒`（4 卡约 `9.8 分钟`）的重复加载开销。

### 3.4 Stage 3：FFmpeg 无损拼接与跨段切口连续性实测（T5 & T7 验证）

- **无损拼接帧数精度**：对已完成的连续三段（`Span 0006 + 0007 + 0008`，时长合计 `296.16s`）执行 `normalize_fragment()` 与 `concatenate_fragments()`，原始分片解码帧数 `5,730 + 5,444 + 6,578 = 17,752` 帧，拼接后输出视频解码帧数 **`17,752` 帧**，零丢帧、零重复帧，PTS 严格单调递增。
- **跨段切口接缝量化分析**：
  - 在无码安静关键帧切开的边界（`Cut 0122 -> 0123`，`pts=7334193`）：原片帧间 `source_L1 = 1.30`，修复片跨段帧间 `restored_L1 = 1.26`（差值 **`delta = 0.05`**，与原片自然帧间过渡完全一致，零接缝零闪烁）。
  - 在改造前强制于连续马赛克中间切开的边界（`Cut 0006 -> 0007` 与 `Cut 0066 -> 0067`）：背景区中位数差值 `p50 L1 = 2.33` 正常，但马赛克修复区（`p95 L1 = 23.67`）因两段独立去噪无跨界滑窗重叠产生单帧纹理跳变（全帧 `L1 delta = +3.79 ~ +4.64`）。
  - 启用 T7 按卡大块归并后，该样本全部 **6 个渲染大块的切点 100% 落在无码间隙内（马赛克内部切点为 0）**，彻底消除跨段切口纹理跳变。
